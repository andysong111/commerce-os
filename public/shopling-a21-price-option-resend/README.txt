Commerce OS · Shopling A21 Price/Option Resend v0.4.0

목적
- Commerce OS에서 Shopling 저장 가격 재조회까지 VERIFIED 된 GOODSKEY만 A21 쇼핑몰상품수정에서 마켓으로 수정전송합니다.
- 판매가와 옵션은 동시에 겹치지 않게 1개 작업씩 처리합니다.
- 마켓별 성공/실패 결과는 검증하지 않습니다.
- 실제 Shopling 결과문서 내부에서 처리중 로딩 종료를 직접 감지한 뒤 다음 작업으로 진행합니다.

v0.4.0 핵심
- v0.2.7에서 옵션전송까지 정상적으로 이어졌던 completeJob → 다음 큐 실행 구조는 그대로 유지합니다.
- v0.3.9의 A21 최종전송일 재조회는 실기에서 수정전송 후에도 값이 갱신되지 않아 완료판정에서 제거했습니다.
- 결과창을 background가 바깥에서 찾고 읽는 방식 대신, result-watch-v040.js를 실제 Shopling 결과문서 자체에 주입합니다.
- manifest의 match_about_blank + match_origin_as_fallback + all_frames를 사용해 일반 Shopling URL뿐 아니라 about:blank/상속 origin 팝업과 프레임까지 감지합니다.
- 결과문서 내부에서 '처리중입니다' 또는 '잠시만 기다려주시기 바랍니다'를 직접 보고 background에 상태를 self-report합니다.
- 실제 결과문서 감지기는 결과 화면을 자동으로 맨 아래까지 스크롤하여 '상품 수정 전송이 완료되었습니다.' footer도 보조 완료 신호로 확보합니다.
- 처리중 표시를 실제로 본 뒤 사라졌거나 완료 footer가 확인되고 1.8초 안정된 뒤에만 completeJob()을 호출합니다.
- 결과 내용의 성공/실패, 도매창고/투비즈온 등 개별 마켓 실패는 진행 차단 조건으로 사용하지 않습니다.
- 전체 실행은 모든 PRICE 배치를 먼저 처리한 뒤 OPTION 배치를 처리합니다.
- 205 GOODSKEY: 판매가 200 → 판매가 5 → 옵션 200 → 옵션 5.

안전장치
1) Shopling 저장 가격 VERIFIED가 아니면 시작하지 않습니다.
2) 배송정보 수정안함과 판매가/옵션 form 값은 송신 전에 검증합니다.
3) Shopling 원본 송신 함수 자체가 실패하거나 예상하지 못한 확인창이 나오면 해당 작업은 실패합니다.
4) 실제 결과문서와 현재 작업의 popup/worker opener 관계를 확인해 오래된 결과창을 현재 작업으로 잘못 귀속시키지 않습니다.
5) 여러 frame의 상태를 합쳐 하나라도 처리중이면 다음 단계로 넘어가지 않습니다.
6) 처리중을 직접 보지 못한 경우에는 실제 결과문서의 완료 footer를 확인하기 전까지 완료하지 않습니다.
7) 결과문서 완료를 30분 동안 확인하지 못하면 V040_RESULT_DOCUMENT_TIMEOUT으로 안전 중단합니다.

사용
1) 기존 확장프로그램을 제거하고 v0.4.0 ZIP을 설치합니다.
2) 이전 실행은 안전 중지하고 남아 있는 Shopling 결과창을 닫습니다.
3) 먼저 1 GOODSKEY 안전 테스트를 실행합니다.
4) 판매가 결과창이 열리면 실제 결과 화면이 자동으로 아래쪽으로 이동하는지 확인합니다.
5) 확장 UI에서 '실제 결과문서에서 처리중입니다 확인' → '실제 결과문서 로딩 종료 확인' → 판매가 SUCCEEDED → 옵션 송신 순서를 확인합니다.
6) 옵션도 같은 방식으로 완료되면 전체 가격·옵션 수정전송을 실행합니다.

주의
- SUCCEEDED는 Shopling 실제 결과문서의 로딩 종료까지 확인됐다는 의미이며 개별 마켓 최종 성공을 보증하지 않습니다.
