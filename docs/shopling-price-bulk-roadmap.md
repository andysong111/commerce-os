# 샵플링 가격설정 Bulk 로드맵

## 목표

최대 20,000개의 `goods_key`를 카나리 검증 후 최대 50개 청크로 안전하게 순차 실행하고, 브라우저를 닫아도 작업 상태를 복구하며, 실패 상품만 제한적으로 재시도한다.

## 100점 기준 진행표

| 단계 | 누적 점수 | 상태 | 완료 기준 |
| --- | ---: | --- | --- |
| 1. 입력·검증·미리보기 | 15 | 완료 | CSV/XLSX/붙여넣기, 숫자 검증, 중복 제거, 20,000개 제한, 청크 예상 |
| 2. 준비 작업 영속 저장 | 35 | 완료 | Supabase job/items/chunks 원자적 저장, 최근 작업 및 상세 복구 |
| 3. 수동 카나리 실행·결과 확인 | 55 | 완료 · goods_key 115835 운영 카나리 검증 성공 | 실제 1~10개만 명시적 확인 후 실행, exact request_id 결과 저장, 일반 청크 자동 실행 금지 |
| 4. 일반 청크 수동 승인·직렬 실행 | 75 | 완료 · 61개 운영 검증 성공 | 카나리 10개 성공 후 normal 50개와 1개를 한 청크씩 순서대로 실행, 중복 dispatch 0건, Shopling 실제 반영 경계 확인 |
| 5. 실패 상품 제한 재시도·복구 | 90 | 개발 중 · 운영 검증 전 | 명시적 실패 goods_key만 최대 2회 재시도, 불명확 결과 차단, 일시중지·재개, 여러 탭 중복 방지 |
| 6. 운영 검증·관측·정리 | 100 | 예정 | 소규모/중규모/대규모 검증, 진행률·감사 로그, 오래된 준비 작업 정리 |

## 안전 원칙

- 기존 50개 이하 즉시 실행기는 독립적으로 유지한다.
- 카나리·일반·재시도 청크는 동일한 기존 가격설정 워크플로를 사용한다.
- 실제 쓰기 전 사용자 확인을 요구한다.
- exact `request_id` 결과만 수용한다.
- GitHub Actions 전송 응답이 불확실하면 재전송하지 않고 기존 결과만 확인한다.
- 카나리 성공만으로 일반 청크를 자동 시작하지 않는다.
- 실패 상품을 특정할 수 없으면 자동 재시도하지 않는다.
- 이미 성공한 상품은 재시도 대상에 포함하지 않는다.
- Supabase service role은 서버에서만 사용한다.

현재 공식 운영 점수는 **75/100**이다. 5단계 코드를 배포한 뒤 실제 실패 상품 제한 재시도와 일시중지·재개를 운영 환경에서 검증하기 전까지 점수를 올리지 않는다.

일반 청크 승인 상태와 실행 결과는 DB에 보존된다. 브라우저를 닫아도 이미 시작한 GitHub Actions는 계속 실행되며, 다시 접속하면 실행 중 결과 조회 또는 다음 대기 청크부터 재개한다. 실패 및 전송 여부 불확실 상태에서는 자동 재전송하지 않는다.

## 5단계 — 실패 상품 제한 재시도와 복구

- 현재 공식 운영 점수는 **75/100**이며 migration 적용과 실제 실패·복구 운영 실증 전까지 유지한다.
- 5단계 코드 목표는 **90/100**이다.
- 재시도는 DB에서 `failed`로 확정된 상품만 대상으로 하며 성공 상품은 절대 재실행하지 않는다.
- 재시도는 최대 2회, 청크당 최대 50개로 제한하고 매 회 사용자 승인을 요구한다.
- 실패 범위를 특정할 수 없는 재시도 결과는 다음 재시도를 차단한다.
- 한 재시도 회차가 조기 실패하면 같은 회차의 미실행 청크는 `superseded`로 종료하고, 다음 회차는 여전히 `failed`인 상품만 다시 구성한다.
- 일시중지는 현재 활성 청크가 완료된 후 적용하며 재개 시 가장 앞의 pending 청크부터 진행한다.
- `dispatch_uncertain`에서는 새 요청을 전송하지 않고 기존 `request_id` 결과만 확인한다.
- 화면의 실패 목록은 100개까지만 미리보기로 표시하되, 복사 기능은 인증된 전체 목록 API를 통해 최대 20,000개를 모두 가져온다.
