# 샵플링 가격설정 Bulk 운영 절차서

## 고정 운영 주소

`https://commerce-os-ops-center.vercel.app/shopling-price-modify-runner`

Preview 고유 주소는 운영 검증 주소로 사용하지 않는다.

## 1. 일상 실행 순서

1. CSV/XLSX 또는 직접 붙여넣기로 goods_key를 입력한다.
2. 유효 수, 중복, invalid, 예상 청크 수를 확인한다.
3. Bulk 준비 작업을 저장한다. 이 단계에서는 가격이 변경되지 않는다.
4. 카나리 최대 10개를 실제 실행한다.
5. Shopling 수정일과 쇼핑몰별 가격을 확인한다.
6. 카나리 성공 후 일반 상품 직렬 실행을 명시적으로 승인한다.
7. 한 번에 한 청크만 실행되는지 확인한다.
8. 완료 화면에서 성공·실패·대기 수와 청크 수를 확인한다.
9. 운영 리포트 JSON과 상품 결과 CSV를 보관한다.

## 2. 200~500개 중규모 검증

각 청크마다 다음 세 상품을 표본 확인한다.

- 첫 상품
- 중간 상품
- 마지막 상품

추가로 전체 작업의 첫 상품과 마지막 상품을 확인한다.

판정 기준:

- 운영 리포트의 전체 상품 수와 입력 목록 수가 같다.
- 성공 + 실패 + 대기 = 전체 상품 수다.
- 청크 수가 `카나리 1 + ceil((전체-10)/50)`과 같다.
- 한 청크가 성공하기 전에 다음 청크 request_id가 생성되지 않는다.
- Shopling 수정일 경계가 실행 목록의 첫·마지막 goods_key와 일치한다.
- 동일 goods_key의 중복 dispatch가 없다.
- 리포트의 경과 시간과 성공 상품/분 값이 비정상적으로 비어 있지 않다.

## 3. 실패 상품만 재시도

1. 실패 화면에서 실패 goods_key 수와 목록을 확인한다.
2. 실패 목록 전체 복사 기능으로 목록을 보관한다.
3. 실패 범위가 특정되지 않으면 재실행하지 않는다.
4. `실패 상품 N개만 재실행 승인`을 누른다.
5. 성공 상품이 새 retry 청크에 포함되지 않았는지 감사 로그와 request_id로 확인한다.
6. 재시도는 최대 2회이며 자동 무한 재시도하지 않는다.

## 4. 일시중지·재접속·재개

1. normal 또는 retry 청크 실행 중 `현재 청크 완료 후 일시중지`를 누른다.
2. 현재 청크는 끝까지 실행되고 다음 청크는 시작하지 않는지 확인한다.
3. 일시중지 상태의 성공·대기 수와 작업 URL을 기록한다.
4. 탭을 닫고 같은 URL로 재접속한다.
5. 상태와 수량이 복구되는지 확인한다.
6. `직렬 실행 재개`를 누른다.
7. 가장 앞의 pending 청크부터 한 번만 실행되는지 확인한다.

## 5. dispatch_uncertain 대응

- 새 실행을 만들지 않는다.
- GitHub Actions의 기존 request_id 결과만 확인한다.
- GitHub 화면의 Re-run jobs를 누르지 않는다.
- OPS 화면의 오류 내용과 request_id를 복사한다.
- 결과가 발견되면 기존 청크에만 반영한다.
- 결과를 찾지 못한 상태에서 같은 상품을 수동 재전송하지 않는다.

## 6. 20,000개 가격 무쓰기 검증

### 브라우저 로컬 검증

1. `20,000개 로컬 파싱 검증`을 누른다.
2. 다음 값이 정확한지 확인한다.
   - valid 20,000
   - duplicate 0
   - invalid 0
   - planned chunks 401
   - estimated mall rows 480,000
3. 벤치마크 JSON을 다운로드한다.

### DB 검증 전용 작업

1. `20,000개 검증 전용 작업 저장`을 누른다.
2. 합성 goods_key만 저장되며 가격 쓰기가 없다는 확인창을 승인한다.
3. 작업 상세에서 다음을 확인한다.
   - 실행 모드: 가격 무쓰기 검증
   - 전체 상품 20,000
   - 전체 청크 401
   - 카나리 계획 10
   - normal 계획 400
   - 가격 실행 잠금
4. 탭을 닫고 같은 URL에 재접속한다.
5. 수량과 잠금 상태가 복구되는지 확인한다.
6. 실행 버튼이 나타나면 실패 판정하고 즉시 중단한다.

## 7. 리포트·감사 로그

- 운영 리포트 JSON: 작업·청크·상품 상태와 처리시간을 보관한다.
- 상품 결과 CSV: goods_key별 상태와 시도 횟수를 확인한다.
- 감사 로그: 상태 변화, request_id 할당, 보관·복구 이력을 확인한다.
- CSV를 열 때 수식으로 해석될 수 있는 값은 안전하게 중화돼 있어야 한다.
- 토큰, Authorization, apikey, JWT, 정책 원문, raw result summary가 노출되면 실패다.

## 8. 작업 보관·복구·오래된 작업 정리

- 완료·실패·검증 작업은 `작업 보관`으로 숨길 수 있다.
- 보관은 삭제가 아니며 `보관 해제`로 복구한다.
- active/running/dispatch_uncertain 청크가 있는 작업은 보관하지 않는다.
- `오래된 준비·검증 작업 보관`은 실행 이력이 없는 prepared/validation-only 작업만 대상으로 한다.
- 자동 정리나 hard delete는 사용하지 않는다.

## 9. 장애 체크리스트

1. 고정 Production 주소인지 확인한다.
2. 작업번호와 request_id를 기록한다.
3. 성공·실패·대기 수 합계가 전체와 일치하는지 확인한다.
4. 활성 청크가 하나뿐인지 확인한다.
5. dispatch_uncertain이면 재전송을 금지한다.
6. 실패 범위가 불명확하면 retry를 금지한다.
7. 감사 로그와 운영 리포트를 다운로드한다.
8. 실제 Shopling 수정일의 첫·마지막 경계를 확인한다.
9. 중복 또는 누락 의심 시 다음 청크 승인을 중단한다.
10. rollback은 가격을 추측해 덮어쓰지 않고, 원본 가격 자료와 기존 가격 엔진의 명시적 작업으로 별도 수행한다.

## 10. 100점 최종 판정

- 200~500개 live 실행 성공
- 20,000개 로컬 검증 성공
- 20,000개 DB 검증 전용 작업 저장·재접속 성공
- validation-only 가격 실행 잠금 확인
- JSON·CSV·감사 로그 정상
- 보관·복구·오래된 작업 보관 정상
- 누락·중복 dispatch 0건
- 운영 절차서와 실제 화면 일치
