# Product Master Shopling 판매원장 증분 동기화 계획

## 목적

최초 24개월 판매원장 적재가 완료된 뒤에는 과거 24개월을 반복 조회하지 않고, 최근 변경 가능 구간만 자동으로 다시 계산해 Product Master의 기존 Shopling 월 판매원장을 갱신한다.

## 안전 원칙

- 최초 24개월 backfill이 `COMPLETED`이 아니면 증분 동기화를 시작하지 않는다.
- Shopling은 주문 읽기 API만 사용한다.
- Product Master에는 기존 `salesMonthly` 통합 경로만 사용한다.
- 기존 Shopling 원장 ID `shopling-sales-v1:<barcode>:<YYYY-MM>`와 source `shopling_orders_24m_v1`를 그대로 사용해 같은 월을 갱신한다.
- 조회 구간 시작일은 반드시 월 1일이다. 월 중간부터 읽은 부분합으로 전체 월 원장을 덮어쓰지 않는다.
- 현재월 포함 최근 4개 달을 재계산한다. 이 범위에서 취소·반품·환불 상태가 뒤늦게 바뀐 주문도 다시 계산한다.
- 재계산 결과에서 사라진 기존 Shopling 월 원장은 0으로 덮어써 취소·환불 후 과거 수량이 남지 않게 한다.
- 유효 주문 중 현재 Product Master SKU로 연결되지 않는 주문이 1건이라도 있으면 해당 실행 전체를 쓰지 않는다.
- 같은 SKU·월에 다른 원천의 판매원장이 있으면 이중계상 위험으로 차단한다.
- 읽기 시작과 쓰기 직전의 mapping fingerprint가 다르면 중단한다.
- 모든 쓰기는 결정적 ID + upsert로 멱등 재시도 가능해야 한다.

## 실행 구조

1. 1시간 예약 Worker가 실행 조건 확인
2. 최초 24개월 판매원장 `COMPLETED` 확인
3. 마지막 성공 증분 실행 이후 1시간이 지나지 않았으면 종료
4. 현재월 포함 최근 4개 달의 월 1일부터 오늘까지 30일 이하 구간으로 분할
5. 한 Worker 호출당 1개 구간만 Shopling 주문 읽기
6. 전 구간 완료 후 월별 판매량 재계산
7. 미연결/충돌/mapping 변경 0건 확인
8. 기존 Shopling 원장 중 새 계산에 없는 행은 0행으로 보정
9. 최대 500행씩 Product Master upsert
10. Product Master 판매원장 snapshot 재조회 후 전수 검증
11. 성공 원장 기록

## 범위 밖 지연 클레임

현재 Shopling 주문 API가 오래된 주문의 최종 클레임 상태를 어느 시점까지 보정해 반환하는지는 별도 검증이 필요하다. 따라서 증분 동기화는 우선 최근 4개 달을 안전하게 재계산하고, 4개월보다 오래된 지연 반품/환불을 다루는 장기 repair 정책은 실제 운영 데이터와 Shopling 응답을 검증한 뒤 별도 추가한다. 추측으로 claims 수량을 차감하지 않는다.
